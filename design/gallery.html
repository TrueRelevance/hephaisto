Verification rows

The T+60s / T+5m / T+15m checks on an executed action. This is the evidence for “everything it does is verified, then reverted if it did not work” — the safety claim on the landing page — and until v0.7.0 it was written to the database and rendered nowhere (backlog #96). All four outcomes appear here because the one that is easy to get wrong is inconclusive: it is blue rather than red on purpose, because a check that could not run has learned nothing and the agent does not roll back on it.

Connections panel

Backlog #111. Every dependency below already described itself at startup and the description went into a log line, so “is it actually working?” was answerable only by reading pod logs.

Four states, and the fourth is the point. not configured is a deliberate choice — every outbound integration here degrades silently when unset, and that is correct per delivery. Painting it red would make a correct install look broken, and a panel that is wrong on a correct install is one people stop reading.

+ postgres Connected. · checked 12s ago + kubernetes Reachable; list namespaces returned 1. · checked 12s ago ~ grafana-mcp 13 of 17 tools; missing query_tempo_traces, query_tempo_traceql, list_tempo_tag_names, list_tempo_tag_values. · checked 12s ago !! grafana-annotations http://grafana.grafana answered HTTP 401. · checked 12s ago - notifications No channel is configured, so nothing is delivered anywhere. · checked 12s ago

The degraded row is the one that earns the state: a grafana-mcp that is connected but started without Tempo registers none of the four trace tools, so the agent cannot follow an exemplar into a trace. That is backlog #31, and the measured reason c10 spent thirteen steps and produced no finding. A binary up/down row would have been green throughout.

Planner
